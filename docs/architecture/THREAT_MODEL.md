# Security and privacy threat model

> Research and educational use only. Not a medical device and not intended for clinical diagnosis or treatment.

The trust boundaries are browser to TLS ingress, ingress to API, API to PostgreSQL and Redis, and the worker to those backends. Offline imaging commands and experiment tracking operate in an independently controlled research environment. Threat actors include unauthenticated callers, compromised research accounts, malicious data providers, and users with access to backups or telemetry.

| Threat | Current controls | Residual risk and deployment responsibility |
| --- | --- | --- |
| Credential theft or cross-owner access | Bearer auth before protected request processing, server-generated UUIDs, owner-scoped scans/results/jobs, constant-time comparisons for static credentials, and 404 for inaccessible objects. | Terminate TLS at the trusted edge. The built-in deployment token represents one shared principal. Use distinct principals for separate research users and rotate credentials. |
| Path traversal or upload type confusion | The HTTP upload protocol ignores client filenames and `Content-Disposition`. It uses a server-controlled name for the declared format, checks the MIME declaration and binary header, and uses fixed export filenames. | The offline CLI reads operator-controlled paths. Keep its input directory and staging environment isolated. |
| Archive bombs and resource exhaustion | ZIP, multipart and generic archives are unsupported. HTTP upload size, decoded gzip bytes, voxel dimensions/count, concurrent protected requests, shared quotas, and authenticated request rates are bounded. | Limits reduce exposure to single requests. Set edge timeouts and connection limits for slow or unauthenticated floods. Capacity-test quota settings and isolate workers. |
| PHI leakage through inputs, artifacts, or backups | The API accepts reviewed NIfTI and keeps decoded arrays and allowlisted metadata. Raw file names, NIfTI header extensions and comments are discarded. Local DICOM ingestion has restrictive checks. | Pixel data can contain identifiers or recognizable anatomy. Derived arrays, reports, hashes, and backups remain restricted research data. Set retention and deletion policies for all copies. |
| Browser injection and unintended data caching | Content-type sniffing, framing and referrer policies, no-store API responses, sandboxed HTML exports, frontend CSP, and memory-only bearer credential handling in the web UI. | Treat downloaded HTML and files as research artifacts. Keep API and browser on the same trusted origin. |
| Supply-chain compromise or unsafe artifacts | Python and npm advisory checks, redacted history scanning, security linting, and a medical file suffix gate. Durable array decoding disables pickle. | Review package and image updates and verify trusted artifact provenance. Use only trusted model files and keep research storage out of public package and CI artifacts. |
| Log or metrics disclosure | Audit events use route templates, generated request IDs, status and a stable principal digest. Metrics use bounded labels. Exceptions, body fields, raw URL paths and query strings are excluded from these events. | Protect logs as sensitive operational records. An opaque principal digest is pseudonymous and linkable. Keep scrape endpoints on the private network and review proxy/SDK logging settings. |

## Authentication and authorization

`Authenticator` resolves credentials to an opaque stable principal. Owner scoping in the artifact and job adapters enforces isolation across all research routes, including outputs and exports. The liveness/readiness and OpenAPI endpoints are public. Only the deployment factory enables the private API metrics endpoint. The current architecture has one owner role per principal.

For a multi-user deployment, inject an authenticator that validates issuer, audience, expiry and signatures of short-lived tokens from the operator's identity provider. Map verified subjects to opaque IDs without using emails or medical identifiers. Apply route-specific roles at the authorization layer if the deployment needs permissions beyond ownership. Keep a distinct operator role for infrastructure and use a restricted database runtime role. The repository's bearer adapter implements local and controlled single-principal deployment access.

## Research imaging review and retention

1. Use synthetic inputs for development, CI, demos and issue reproduction. Real patient data, private images and related identifiers must never enter Git, even if a repository or fork is private.
2. Perform de-identification in an approved environment before import. For DICOM, review identifying tags, dates and times, UIDs, private elements, overlays and descriptors. Choose the applicable DICOM confidentiality profile and options with the data steward. Review burned-in pixel text and recognizable features in reconstructions, including facial anatomy. Consider defacing where it is suitable for the research and document any scientific impact. [DICOM PS3.15 confidentiality options](https://dicom.nema.org/Medical/Dicom/current/output/chtml/part15/sect_E.3.html)
3. Verify NIfTI conversions separately. Inspect metadata, filenames, sidecars and the reconstructed volume. Send only the approved volume. Uploads require the caller's attestation. Independent de-identification review happens before ingestion.
4. Restrict access to source and derived outputs. Apply retention to scans, jobs and all derivatives. Deleting a scan is a logical deletion and does not erase results derived from it, database backups, or audit records. Delete obsolete terminal jobs and their artifacts independently, and expire protected backups on the approved schedule.
5. If a suspected disclosure occurs, stop processing and follow the data steward's incident procedure. Report a platform vulnerability privately with a synthetic reproduction. [Security policy](../../SECURITY.md)
